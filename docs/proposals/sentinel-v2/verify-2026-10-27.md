## V-1: the scan process as it is

Measured on `main` at `5aad3a6b` (the build the worktree was handed; the later `358a1006` touches no Sentinel source),
macOS arm64, Node 24.21.0, no Docker (`SENTINEL_ISOLATION` unset). Every command was the installed executable
`packages/sentinel/dist/cli.js`, run under `/usr/bin/time -l` in a scratch copy of `examples/invoice-app` (44 captured
files) inside the worktree's `build/`, with the owner's trust state in a separate `XDG_STATE_HOME` and `HOME` untouched
(Copilot's native login needs it). For each command the raw argv, stdout, stderr, exit code, peak RSS and wall time
are kept in the owner's private review folder, not here; this file quotes only what a reader needs.

The one live model run: `run <id> --confirm --confirm-models`, provider `native-copilot` (`copilot-cli`), model
`gpt-6-luna`, settings as the package README's *Copilot CLI foreground review* and *Agentic-only review without
external scanners* sections configure them today, Copilot CLI 1.0.103. It made three model calls in 50.6 s.

### The five biggest gaps, confirmed or corrected

README §10 names five gaps that decide the slice. All five hold; two need a correction or a sharper statement.

1. **No `scan` verb and no run list: confirmed, with one correction.** `farsight-sentinel scan` answers
   *unknown command: scan* (exit 3), and `cli/args.ts:6-34` has no `scan` and no run-list verb. There is **no
   general-purpose service or CLI list operation**, but the service does expose a run list to the companion by
   delegation: `service/owner-service.ts:222-224` hands every `owner-ui.*` op to `owner-ui/operations.ts:157-177`, whose
   `owner-ui.runs` the companion calls (`owner-ui/server.ts:389-392`). It reads 65 rows from `store.ledger.listRuns`
   and shows at most 64, using the extra row only for `more` (`owner-ui/process.ts:27-37`). So the data for SCANS and a
   paired-owner path to it exist; the CLI and the MCP tools (`service/mcp.ts:26-89`) have no way to ask for it.
2. **Reads refused while the service holds the store: confirmed, and narrower than §5.2 says.** With a service up,
   `status`, the minimal `report` and `wait` go through it and answer (`cli.ts:507-530`, `cli.ts:755-779`); `run
   --detach` works. What refuses with *the workspace's service holds the store* (exit 3) is exactly §10's list:
   `report --full`, `compare` (`cli.ts:672-678`), `report --instructions` (`cli.ts:337-346`) and `plan`, `paths`,
   foreground `run`, `retry`, `rerun` (`cli.ts:493-506`). §5.2's sentence that `status` and `report` refuse is stale.
3. **The stage set derived, closed and sealed: confirmed.** The static profile plans three bootstrap units (capture,
   parse, inventory; `planner/planner.ts:257`) and then 30 check units, one per source file under the one preview rule
   (`planner/planner.ts:368`); the agentic-only settings plan the same bootstrap and one appended `review-general` unit
   (`review/plan.ts:28`). Nothing the owner writes declares a stage. The agentic-only plan is labelled `deterministic`
   and its plan line says *The pinned scanners report observations and exact required coverage* although no scanner
   is planned (`cli.ts:596`, `strings-sentinel-service.ts:80`).
4. **Both CLIs stripped to single-turn text engines with skills `[]`: confirmed, and the live run shows what it costs.**
   The Copilot argv excludes every built-in, MCP and custom tool and turns custom instructions off
   (`review/providers/cli-copilot-call.ts:17-50`); skills are passed as `[]` (`service/review-adapter.ts:80`); a Copilot
   review gets three Sentinel turns and 120 s (`service/review-adapter.ts:76`), each turn one Copilot process. A final
   answer is accepted on any of the three turns (`review/session.ts:581-590`). **Measured:** on the invoice-app fixture
   this run exhausted its three turns without a final answer: it listed the partition, read `src/server/routes.ts` and
   read `src/server/auth.ts`, and the step limit (`sentinel.review.frontier.steps`) ended it **unfinished, 2 of 30
   partition files inspected, 0 observations**. The retained record says `skills: []` and
   `vendorSkillDiscovery: not-performed`.
   **Recommendation, separate from the measurement:** one run is not a rate, but a three-turn list-then-read loop
   leaves little room for an answer over a 30-file partition; A-2's native mode, or a turn budget sized to the
   partition, should be measured on this fixture before the slice relies on the review stage producing observations.
5. **The UI an iframe with no door from a source: confirmed by reading.** `surfaces/sentinel.js:116-122` (155 lines,
   not the 20 of §5.1) builds the iframe to the companion origin from `GET /api/sentinel/companion`
   (`packages/server/src/index.ts:1230`); there is no Scan button and nothing links a source to it. V-2 drives it.

Beyond the five, V-1 found five more that the slice will trip over (each in the tables below):

- **Human output crashes on any refusal code outside three catalogs.** `word()` in `cli.ts:52-57` looks only in the
  decision, CLI and service catalogs and throws for any other key; `serviceOut` (`cli.ts:279-281`) calls it on every
  reason. So `capabilities` dies after two rows (row 3's reason lives in `strings-sentinel-capture.ts`), and `run <model plan>
  --detach --confirm` prints *the command could not finish (Error)* instead of `sentinel.review.foregroundRequired`
  (`strings-sentinel-review.ts`). `--json` output is unaffected. The plan names only the capabilities symptom.
- **A refused model unit leaves no reason anywhere.** With the owner's own `PATH`, the run ended *completed* with
  *a planned check failed to execute*; `status` says `completed`; `report --instructions` says *the review read bytes
  that are not what was captured*. The real reason (Copilot discovery, next item) is set only in memory
  (`execution/coordinator.ts:1146-1147`, `#failedUnstarted`) because the review is prepared before the attempt is
  recorded (`execution/coordinator.ts:1166-1168`); the ledger keeps only `outcome: execution-failure`.
- **The model review's result reaches no report.** After the live run, `report <id>` says *the run did not complete*
  (`service/local.ts:907-914`: no scanner and no preview findings) while `status` says `completed`; `report --full`
  prints 0 observations, 0 gaps, *44 of 44 captured files seen by no check*, and no model, turns, tokens or the
  unfinished review. The turns, tokens and unfinished scope are only in the private `report --instructions --json`
  (54 KB of JSON); the model identity also reaches the companion's process view.
- **Copilot discovery is the first `copilot` on `PATH`** (`review/providers/cli-copilot-profile.ts:227-245`). See the
  qualified-Copilot row: this corrects §10.
- **The commands that build the adapter registry pay for it in every process.** `publicRegistry`
  (`service/scanner-profile.ts:31-48`) is built on first use and cached for the process; the first construction took
  2.6 s and +279 MiB in isolation, the second call 37 ms and +0. `plan`, foreground `run`, `rerun`, CLI `status` and the
  service at start (`service/owner-service.ts:172`) build it, so `status`, a read, peaks at 370 MiB and 1.2 to 2.2 s, as
  much as `plan`; through the live service the same `status` is 131 MiB and 0.24 s. `help` and `version` never build
  it (`cli.ts:814-822`), nor do `init`, `settings`, `rules` and both reports (130 to 168 MiB). Their 130 MiB floor is
  the import graph: bare Node is 42 MiB, and importing `service/local.js` alone reaches 123 MiB, because `cli.ts`
  imports every service module eagerly.

### What a first-time user hits, in order

The reader followed the package README with no knowledge of the plan, on the invoice-app copy.

1. `capabilities` prints two rows, then *the command could not finish (Error)*, exit 3. `--json` works and lists 28
   capabilities, each with `plannedIn: "PR 02"` to `"PR 26"`.
2. `init --profile static` ends *next: review the file, then adopt it as its owner (available with PR 06), then plan a
   scan (available with PR 09)*. It does not mention `rules promote`. `init --profile agentic` is *unknown scan profile*.
3. `init --profile scanners` on the existing file says *kept … unchanged* and then *profile: scanners*; the file is
   still the static profile (`cli/init.ts:193` reports the requested profile, `cli.ts:257` prints it).
4. `settings adopt` without `--confirm`: *waiting for the owner to confirm* (exit 4); it does not say which flag.
5. `plan` (and `plan --confirm`): `sentinel.service.noRuleLock: sentinel.service.noRuleLock`, the raw code twice, no
   hint (`cli.ts:640`). `rules show` prints only *answered*. The missing step is `rules promote
   builtin:foundation-preview --confirm`.
6. `plan` then works without `--confirm`; `--confirm` changes nothing under init's grants. It prints `plan run-… ·
   sha256:… · effects: local-artifacts · Foundation preview …`. The id is called a plan but is the run id, and the user
   retypes it into `run`, `status`, `report` and `report --full`.
7. `run <id>` runs without `--confirm` (9.0 s) and ends exit 2: *required checks did not complete: foundation preview
   complete: this is not required coverage*. The happy path of the shipped default exits 2.
8. `status <id>` prints the state and *answered*; no unit, attempt or event is shown (`--json` pages the events, 20
   at a time).
9. `report` says *1 folder never listed in the captured files*; `report --full` says *0 folders never listed*: one
   unit and scope, two numbers (`service/local.ts:917` counts the excluded held store, `service/full-report.ts:537-539`
   drops excluded folders; the catalog's own define says excluded folders count). The full report's Markdown, printed
   to a terminal, escapes every `.` and `-` (`report\.e74…`, `run\-f56b…`) and ends with a glossary that names catalog
   keys (`sentinel.count.findings`).
10. To rerun part of it: `rerun <id> --stage capture` is refused; the user has to find a `work-check-…` id in
    `plan --json`.
11. With a service running (any `run --detach` starts one, idle-stopping after 15 s), `report --full`, `compare` and
    `plan` refuse until it stops.
12. Copilot: `capabilities --models --json` answers `capabilityUntested` on the owner's `PATH`. Nothing says the
    qualified binary is installed elsewhere; after reordering `PATH`, the user copies four profile values by hand into

    `hostedReviewSecretScan`, adds `effects` to the `run.start` grant and a `paid.admit` grant, adopts, plans again
    (a new run id) and is shown a plan line about *pinned scanners* that are not there.
13. `run <id>` on the model plan prints `run run-… · undefined · preview findings: undefined` and *the background

    in `--json`.
14. On the owner's `PATH`, `run --confirm --confirm-models` ends *run … · completed · preview findings: null* and *a

15. With the corrected `PATH`, the live run: 50.6 s, three calls of about 15 s each, exit 2, *required checks did not

16. `report <id>`: *the run did not complete* (exit 3) for a run `status` calls completed. `report --full`: nothing

### Where the product and the plan disagree

- **§5.2, reads while the service runs.** The plan says `status` and `report` refuse with *another Sentinel process owns
  this store*. They answer through the service; §10's list of what refuses is right. P-4's done-when (*`status`,
  `report` and `plan` read through the running service instead of refusing*) needs only `plan`, `report --full`,
  `compare` and `report --instructions`.
- **§10, the qualified Copilot.** The plan says the call is `capabilityUntested` until 1.0.105 is re-qualified. On this
  machine the CLI call is untested only because of `PATH` order; the qualified 1.0.103 is installed and works from the
  CLI. The product is right to refuse unpinned bytes, and the plan's remedy (re-qualify 1.0.105) is still needed. It is
  not the only thing between the slice and a live model stage: the browser refuses model-backed starts
  (`owner-ui/operations.ts:242-247`, `:288-290`) and native mode is unqualified. Discovery should say *found 1.0.105 at
  the first `copilot` on PATH; the qualified 1.0.103 is not that one* rather than `capabilityUntested`.
- **§5.1, the surface.** *A 20-line surface* is 155 lines today; §10 has it right.
- **The brief's command sequence** (`init`, `settings adopt --confirm`, `plan --confirm`, `run <plan> --confirm`)
  omits `rules promote`, without which `plan` refuses; the package README has the step. `--confirm` on `plan` and on a
  model-free `run` is a no-op under init's grants.
- **The product against itself.** `capabilities` says `model-review` is unavailable; the same build ran one. The plan
  line for an agentic-only run speaks of pinned scanners. `status` says completed while `report` says the run did not
  complete. In each case the run's records are right and the words are wrong.
