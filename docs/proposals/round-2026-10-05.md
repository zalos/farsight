## 2. Storylines — a named chain of journeys across features

**The word.** A journey is one feature a person moves through. What the owner calls a *vertical* is the whole life of
one business thing across many features and both personas — an invoice from submission to payment, a vendor from
creation to approval to removal. It is declared, ordered, and crosses persona groups. The word is **storyline**
(code and hybrid registers) · **questline** (business register, beside *quest log* and *fast travel*); *lifecycle*
and *value stream* were considered and are narrower (a storyline need not be one object's life). Renaming is one
catalog entry.

### 2.1 Manifest and config (additive)

```json
{
  "storylines": [
    { "id": "invoice", "name": "An invoice, end to end", "description": "From the contractor's upload to the week it is paid.",
      "journeys": ["contractor-sign-in", "invoice-submission", "invoice-review", "invoice-correction", "invoice-paid", "weekly-cycle"] },
    { "id": "vendor", "name": "A vendor account", "journeys": ["vendor-account-creation", "vendor-account-review", "vendor-id-link"] }
  ]
}
```

- `storylines[]` on a manifest, and on `farsight.config.json → journeys.storylines[]` with the same override rule as
  personas and groups (config entry overrides by id, config order wins, root block then nearest). `journeys[]` are
  flow ids **in order**; an id no manifest in scope declares is a note (`journeys.notes`), never a step; a journey may
  be in several storylines. A storyline may span manifests of one source; cross-source storylines are left open (§8).
- `JourneysMeta.storylines[]` (`{ id, name, description?, journeys: string[], declared: true, from }`), folded at ingest
  beside personas and groups; `JourneyTree.storylines[]` = `{ id, name, description?, journeys: JourneyRow[] (in order,
  each with `stepIndex`), counts: { journeys: Counted, built: Counted }, notes }`; a `JourneyRow` gains
  `storylines: string[]`. Counts: `count.unit.storylines`, scope `count.scope.storyline` (COUNTS.md § Journeys).

### 2.2 Surfaces

- **Map:** a *Storyline* picker in the toolbar (`?storyline=<id>` in the hash, beside `?band=`): the board draws only
  that storyline's journeys, **in storyline order, as one band** (its name as the band word, step numbers on the
  cards, a *then* link between consecutive steps drawn always, at every altitude — this is the one case where the
  board draws links unhovered), every other journey hidden; *All* restores the bands. The Affected mode composes
  with it. The explore card and the property head print *in storyline: <name> · step n of m*.
- **Journeys front door:** a *Storylines* section above the personas (one card per storyline: name, description,
  the journeys as numbered chips, *open on the Map*, *open the journey* on the first step).
- **Journey view:** the header line gains *storyline · step n of m* with *previous* / *next* arrows that open the
  neighbouring journey at its first step.
- **MCP `journeys`** gains `storyline?`; the text prints a *Storylines* block first; `graph_overview` counts them.
  **CLI `farsight journeys --storyline <id>`**. `design_guide` documents it.

## 3. The Map and the journey open each other; details link out

### 3.1 One address, two pictures

- **Map → journey.** A screen on the street and the property head get *open the journey here*:
  `#/journeys/<flowNodeId>?step=<n>` opens the blueprint timeline with step *n* (the screen's segment) selected and
  scrolled into view, the same lens, the same scope. The explore card of a call or data node opens the journey at
  the segment whose markers include it (`?step=<n>&node=<id>` selects the marker).
- **Journey → Map.** The journey header gets *see it on the Map*: `#/map?j=<flowId>&screen=<n>` opens the street
  with screen *n* framed (the Z lane's `enterJourney` + a settle on the screen); with plumbing on when the journey's
  selected marker is a call or data node (`&p=1&node=<id>` opens that node's explore card).
- Both are `lib/route-url.js` functions (`journeyStepHash`, `mapScreenHash`), pure and tested; the *Copy link*
  controls include them. Existing params are untouched.

### 3.2 Every detail is a door

The rule: **a detail that names something in the graph is a link to where that thing is best read**, in every
register, with the same words the surfaces already use. On the property's tabs, the explore card, the street's chips,
and the journey's marker expansions:

| detail | expands to | links to |
|---|---|---|
| a gate or rule (`guards` / `validates`) | the guard's code lines (the spliced code the journey already draws, read from `/api/source`) | `vsl()` VS Code deep link at the line · the rule node on the code map |
| a call to a route | the contract (method · path · the spec's summary, request/response names) | the APIs surface at that operation (`#/apis/<apiId>?op=<routeId>`) · the spec file at its line (`?view=spec&line=`) · the handler in VS Code |
| a record / store / external | the store line (*Postgres · database record*) and the columns the graph knows | the table or external node on the code map · VS Code at the schema file when `loc` is known |
| a test / evidence chip | the cases named, with status and last run | the Tests surface filtered to the journey (`#/tests?flow=`) · the spec file in VS Code |
| a work chip | title · state · assignee | the item in the Work surface · the tracker URL |
| a screen | its route, its design id, its image | the page node on the code map · the design row · Figma when the manifest names a node |
| a package | version · importers count | *Where is it included* (`#/codemap?view=package&package=`) |

A link to a place the graph does not know (no `loc`, no spec, no tracker URL) is not drawn; the absence word stays.
`lib/detail-links.js` is the one builder (pure, tested): `detailLinks(kind, node, ctx) → [{ word, href, external? }]`,
so the journey view and the Map draw the same doors. Keyboard: Enter on a focused detail opens its first door;
`o` opens it in VS Code.

### 3.3 Map marks left open by the clarity pass

A quieter *stale* mark distinct from *not fully built* (today both are *at risk*): the card shows *stale* in the
muted colour and *not built* in amber, one or both; an 8-px floor on card text (past the floor the board stops
counter-scaling and the fit says so in the footer: *n journeys · zoom in to read*).

## 4. A thousand projects — the browser side

**Target.** A workspace of **1,000 NX projects** (apps and libs across 20 sources), **~250k nodes · ~400k edges**,
with 300 journeys across 40 manifests. Every surface must open and respond on a 2024 laptop in Chromium:

| surface | first draw | an interaction (filter, zoom, open) |
|---|---|---|
| Journeys front door | ≤ 2 s | ≤ 200 ms |
| Map board (300 journeys) | ≤ 3 s | pan/zoom ≥ 30 fps, open a street ≤ 500 ms |
| Code map, grouped by project | ≤ 4 s | a filter ≤ 500 ms |
| Portfolio · APIs · Tests · Changes · Work | ≤ 3 s | ≤ 500 ms |
| ⌘K | — | a keystroke ≤ 50 ms |

**Method.** `scripts/synth-graph.mjs` writes a synthetic `graph.json` of that shape (seeded, deterministic, with
`meta.projects`, `meta.journeys`, design and flow nodes, packages, tests), `e2e/perf/*.pw.spec.ts` serve it and
measure each row with `performance.now()` around the surface's own ready selector, long-task counts and heap size
(`page.metrics()`), and print one table; a `perf` test in `packages/server/test/` holds the model folds under budget
on the same synthetic shape (the way `codemap-perf.test.ts` does). Then fix what the table shows, in the models and
indexes first (`store.js`, `lib/*-model.js`), with virtualised lists where a surface draws every row (the picker's 60
cap is a hint), and only then in the surfaces — a change inside `surfaces/map.js` or `surfaces/journeys.js` is
named in the PR so the lanes that own them this round can merge it. **What is out of scope here and goes in the
proposal's §8:** the `/graph` payload (48 MB today, ~500 MB at this size) — a server-side query API with the same
index semantics is the next ceiling and is a round of its own.

## 5. The fetch-helper parser regression (handoff, first since 2026-10-04 morning)

`fetch(url, helper(ctx, { method: 'POST', … }))` — the method literal in an object-literal argument of a wrapper call
— resolves to the GET route of the same path. In `packages/parsers/src/tsjs.ts` at the `fetch(` site: when the init
argument is a call expression, read a `method:` string literal from its object-literal arguments (spreads included),
the way the class-method path already does; a helper whose name is a verb (`post`, `put`, `patch`, `del`) is the
fallback. A test with that exact shape; re-measure read-only on the reference app (drift 19 → 7, http edges to
routes still 69).
