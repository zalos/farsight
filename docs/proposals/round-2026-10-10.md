# The lanes round — 2026-10-10

Three inputs set this round. The 2026-10-06 swarm (eight personas, cold, on the reference app's own server at
`81a455e`; reports outside the repo) scored **8 × TRIAL, fit 7.0** and named, one level down, the same defect in
every report: *a number whose scope changes between surfaces without saying so*. The owner shared a developer
overview written for the reference app whose one page that works is *the journey at a glance*: lanes per actor, stages
as columns, arrows across lanes where an action moves the record, dashed where a user merely sees a change, and under
it a table of *what the user sees · the internal states · what moved it*. And a study of two open-source products
(a knowledge-graph dashboard that wins readers with a derived guided tour and a persona named by job, but whose prose
is model-written with no evidence or scope; and an agent-memory server with tool tiers, budgeted answers, a
session-start context block and *copy as MCP call* on every record, but which never parses code) showed mechanics
to borrow without their weakness.

The thesis: **draw the storyline as lanes of who acts, with the record's life underneath in words a person wrote,
make every number carry the scope it counts over, and make that picture one stop on a single zoom that runs from
every journey down to the lines of code.** Everything else is a door on that picture.

Before the round, every proposal was mocked as the real screen beside a mock of the proposed screen on the public
`examples/invoice-app` fixture (the mocks, the four lanes' notes and the competitor summary stay outside the repo).
Two findings from the mocking itself are worth keeping: a mock's numbers and orders must agree with the graph exactly
as a real screen's would (the swimlane mock was rebuilt once because its record lane disagreed with the lifecycle
order), and a derived picture can admit a gap where a hand-drawn one cannot (the example app's approve never checks
the prior status, and the mock's arrow says *not checked by the code*).

## Decisions taken by the lead

- **The Map is the surface that stays.** What retires is the separate journey page; its views become stops and
  layouts of the Map. The front door (`#/journeys`) stays. Lane U builds toward that from step 1 and spends nothing
  on parity between the two surfaces; U2 (one address, the redirect, the specs re-addressed, `step=` renamed
  `screen=`) starts when U merges.
- **Lanes are derived, config names.** Persona lanes from the journey tree, store lanes from write edges on the
  storyline's calls, hand-offs from lifecycle transitions whose writer and reader sit in different lanes; a lane or
  hand-off the config names that the graph cannot find is a note, never a drawn arrow.
- **The code decides statuses and moves; config only names them.** An unmapped status prints through `humanize()`.
- **Scope on the chip wherever two scopes can meet.** The tip keeps the breakdown. *Passed* keeps its word and gains
  the skip count; a screen with no code has no verdict.
- **A gate's tier comes from its class** unless config or an annotation says otherwise; the business register never
  lists a use-case as a gate on itself.
- **Nothing is printed that the graph cannot cite.** The tour and the answers are assembled; a model phrasing pass,
  when it comes, is off by default and labelled.
- **The PR comment goes through the same three-verdict gate as tracker writes**; the credential is a keychain
  reference, never a value in a file.

## The lanes

Each lane is an Opus agent in its own worktree under `../farsight-wt/`, with its own e2e ports, measuring on a
read-only copy of the reference app's graph served by its own build, and ending in a PR whose title is the squash
commit. The lead squash-merges in the order below after CI, then runs the ritual (gates · pack · reinstall under both
prefixes · restart 4477 and 4478 · `POST /api/sync`), then dispatches the next wave.

Every lane: the exact CI commands locally before the PR (`pnpm build && pnpm typecheck && pnpm -r test &&
pnpm lint:strings && pnpm e2e`), a measurement on the reference app's graph with zero page errors on every shot, a
report that says what was measured and where the brief was wrong, and nothing from the reference app that names a
client in the PR or the report.

## What this round does not do

A model-written narrative; a persona pill named by job (worth a test on the front door after the tour exists);
publish-and-subscribe and the cross-repository portfolio (both sit on the engines of 6 and 7 and follow them); the
server-side query API round (`/graph` at 245k nodes), which the Map's table layout on a 300-journey graph will need
for the board but not for one journey.
