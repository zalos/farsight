# Farsight Sentinel: scanner and security-standard research

Checked: **2026-10-17**. Farsight code baseline: **`4fce1c8`** (PR #115 merged). Every linked source below was accessed on **2026-10-17**. Status: research supporting a proposal, not an implementation or scanner benchmark. Sources below are upstream documentation, repositories, and license texts. Capabilities, release channels, and commercial terms must be pinned and checked again when an adapter is implemented. No scanner was installed or run for this research.

## Recommended direction

Build Sentinel as the durable evidence and orchestration layer around Farsight, with replaceable scanner adapters. For v1, use Farsight's existing TypeScript/JavaScript **and Java/Spring Boot** adapters through `@farsight/code-parser` at base `4fce1c8`, local parsing and storage, deterministic checks, and explicitly enabled model review. Extend their source facts and framework models into reviewable security slices; use specialist engines where stronger data-flow analysis is needed. A call graph alone does not establish a feasible execution path or prove that a control protects every request.

The proposed default stack is Farsight graph checks plus an original, tested rule pack, with Opengrep as the candidate default pattern engine and Semgrep CE as the comparison in E3; OSV-Scanner for dependency advisories; Gitleaks for secrets; Trivy for infrastructure/container configuration; and zizmor for supported CI configuration. Add user-installed CodeQL under attested applicable terms and Semgrep Code as optional customer-provided engines. Evaluate Joern with versioned Spring semantics against the Java/TS fixture corpus before committing to a deeper analysis engine. Bearer CLI is an additional SAST candidate; its documented Pro cross-file capability must not be attributed to the CLI. Accept imported passive runtime evidence in v1; defer active runtime scanning until its environment and execution controls exist.

These are architectural recommendations. Documentation establishes that the tools expose relevant capabilities; it does not establish their recall, precision, resource cost, or Spring coverage on Farsight's target applications.

## SAST and parsing evidence

**Semgrep CE and Code must be represented as distinct capabilities.** Upstream describes CE as deterministic, offline-capable, and deliberately limited at file boundaries. Its glossary explicitly distinguishes interfile flow from per-file analysis, which can include cross-function analysis within a file. The commercial support matrix lists cross-file data flow and framework-specific control-flow analysis for Java, JavaScript, and TypeScript. Sentinel can use CE matches as locations worth reviewing without overstating their meaning. [CE design](https://semgrep.dev/docs/contributing/semgrep-philosophy), [analysis terminology](https://semgrep.dev/docs/writing-rules/glossary), [language support](https://semgrep.dev/docs/supported-languages).

The engine and rules have separate licensing facts. Semgrep describes CE as LGPL-2.1. The Rules License says “only for your own internal business purposes” and “does not allow you to distribute the rules”; its service restriction must also be read. The rules repository identifies that license for its maintained/community rules. Consequently, the proposal is to ship original Sentinel rules and support separately approved, locally supplied packs, recording a license and origin per pack. Treat permission to redistribute a particular pack as a release requirement, not as a consequence of engine availability. [Engine repository](https://github.com/semgrep/semgrep), [Rules License](https://semgrep.dev/legal/rules-license/), [rules repository](https://github.com/semgrep/semgrep-rules).

Semgrep's December 2024 notice moved some internal JSON/SARIF fields and experimental features into its logged-in commercial engine. Sentinel computes its own finding identity from captured evidence. The proposed local profile uses pinned binaries, local rule files, `--metrics=off`, version checks disabled, no registry `p/…` or `auto` configurations, and no inherited login credentials. Registry configurations violate Sentinel's local-input policy; the license decision is recorded separately per pack. Explicitly record file-size and timeout limits: the CLI reference lists a 1,000,000-byte target limit, 5-second rule/file timeout and threshold of three rule timeouts. A bounded higher limit or disabled tool filter may be selected within the worker budget; silent omission is never completion. [December 2024 changes](https://semgrep.dev/blog/2024/important-updates-to-semgrep-oss), [metrics](https://docs.semgrep.dev/metrics), [CLI reference](https://docs.semgrep.dev/cli-reference), [current glossary](https://docs.semgrep.dev/writing-rules/glossary).

**CodeQL provides the strongest documented fit for an optional mature whole-program query adapter.** Its Java and JavaScript/TypeScript guides expose global data-flow and taint analysis, including source, sink, and barrier modeling. The docs caution that global flow is more expensive and less precise than local flow. Java's remote-input library includes Spring controller/web models. Sentinel should preserve the query's path and assumptions, rather than convert every reported path into a confirmed exploit. [Java flow](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-java/), [JS/TS flow](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-javascript-and-typescript/), [remote sources](https://codeql.github.com/codeql-standard-libraries/java/semmle/code/java/dataflow/FlowSources.qll/type.FlowSources%24RemoteFlowSource.html).

CodeQL's standard queries/libraries are MIT-licensed; the CLI has separate per-user terms. Its Use Rights section distinguishes academic research, demonstrations and testing OSI-licensed queries from analysis of an OSI-licensed codebase. The automated database-generation grant is tied to open source hosted and maintained on GitHub.com; the paid-license exception changes specified restrictions. GitHub's product documentation describes eligible private-repository use through GitHub Code Security. The CLI restrictions include “share, publish, distribute or lend the Software” and “hosted solution”; read their full surrounding clauses rather than equating public visibility with a grant for every workflow. Sentinel never downloads or redistributes the CLI: it detects a user installation and records `entitlement: user-attested`, the applicable terms reference and selected use basis. This is the proposed adapter policy, not a determination that every private-code use has the same terms or that a hosted arrangement is permitted. [Query repository](https://github.com/github/codeql), [CLI availability](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-cli), [CLI terms](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md).

**Joern is a credible local engine candidate, not a turnkey Spring guarantee.** It builds code property graphs and supports Java and JavaScript frontends under Apache-2.0. Its repository currently requires JDK 21; the installation documentation still says JDK 19, so use the selected release's tested requirements. The Java frontend supports extra type-information jars, optional dependency fetching, and Delombok settings. Its documented fallback propagates taint broadly through external methods with no supplied semantics, creating a concrete reason to version framework summaries. The Java frontend README still lists lambda data-flow and try/catch work as TODOs; E3 must test those constructs rather than infer implemented coverage from AST support. A written Spring semantics pack is part of the Joern comparison; the resulting false-positive rate remains unmeasured. [Repository and requirements](https://github.com/joernio/joern), [installation](https://docs.joern.io/installation/), [Java frontend](https://docs.joern.io/frontends/java/), [custom flow semantics](https://docs.joern.io/dataflow-semantics/), [Java frontend README](https://github.com/joernio/joern/blob/master/joern-cli/frontends/javasrc2cpg/README.md), [JavaScript frontend README](https://github.com/joernio/joern/blob/master/joern-cli/frontends/jssrc2cpg/README.md).

**JavaParser is an optional precision enrichment for the Java adapter Farsight already ships.** It supplies a source AST, symbol-to-declaration resolution, and JSON serialization, with Apache or LGPL licensing choices. It does not itself establish Spring dependency injection, security-chain selection, or interprocedural taint. Start with the existing adapter and its measured limitations; evaluate JavaParser or Joern only where a fixture-based spike demonstrates useful additional resolution or flow evidence. Neither is a prerequisite for v1 language support. [JavaParser](https://github.com/javaparser/javaparser).

**Opengrep is the candidate default pattern engine, pending E3.** The LGPL-2.1 fork documents self-contained binaries, `--taint-intrafile` cross-function flow, and JSON/SARIF metavariables and fingerprints. The release list shows 1.31.0 dated 2026-10-15 and a separate interfile alpha channel marked for testing. This supports evaluating its packaging and output stability; it does not establish interfile readiness or accuracy. Pin the exact binary and validate its local-rules, telemetry, skip and timeout behavior in E3/E7. Sentinel's finding identity remains independent of engine fingerprints. [Project](https://github.com/opengrep/opengrep), [project changes](https://github.com/opengrep/opengrep/blob/main/OPENGREP.md), [releases](https://github.com/opengrep/opengrep/releases).

The [opengrep-rules repository](https://github.com/opengrep/opengrep-rules) describes a 2024-12-13 fork for research, testing and benchmarking. Its [LICENSE](https://github.com/opengrep/opengrep-rules/blob/main/LICENSE) identifies LGPL 2.1 with a Commons Clause condition that excludes “the right to Sell the Software.” The existence of a fork does not establish rights to ship its rules. Original Sentinel rules remain the proposal.

**Bearer and bytecode tools are useful comparisons with distinct capabilities.** Bearer CLI documents JS/TS/Java source scanning, while its README places advanced cross-file analysis in Bearer Pro. Its Elastic License 2.0 restriction begins “You may not provide the software to third parties as a hosted or managed service” and is qualified by access to a substantial feature set. The owner's hosted-service question remains open; inclusion in E3 does not decide licensing suitability or promise Pro features. find-sec-bugs supplies Java bytecode checks as a SpotBugs plugin under LGPL-3.0. Producing bytecode from a target may run project build plugins, so this path depends on the unresolved isolated-build decision. [Bearer](https://github.com/Bearer/bearer), [Bearer license](https://github.com/Bearer/bearer/blob/main/LICENSE.txt), [find-sec-bugs](https://github.com/find-sec-bugs/find-sec-bugs), [SonarQube edition comparison](https://www.sonarsource.com/blog/sonarqube-compare-editions/).

## Java/Spring Boot requirements

Source-only parsing should be available without building the target application. However, the report must identify unresolved types, generated code, dependency resolution gaps, and omitted source roots. An optional isolated build profile can improve extraction and record generated-source/build inputs. CodeQL supports Java `none`, `autobuild`, and `manual`; Kotlin requires a build. Crucially, Java `none` can still invoke Maven/Gradle to query dependency information. Its documented accuracy limits include missing generated code, dependency/version ambiguity, and colliding class names. Therefore, “no build” must not be advertised as “no target-controlled tooling executes.” [CodeQL build modes and Java limits](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages).

The Spring model must account for filter registration and order, chain matchers, exclusions, controller mappings, and applicable method security. Spring Security selects the **first matching** `SecurityFilterChain`; finding one secured chain somewhere in the application does not protect every endpoint. A chain without an explicit `securityMatcher` matches all requests by default; if no chain matches, Spring Security does not protect the request. A chain's `requestMatchers` authorization rules apply only inside its `securityMatcher`, and changing the chain matcher does not relocate filter-provided endpoints. Spring's MVC documentation also warns that interceptor and controller path matching may differ. A middleware finding should therefore link its conditions to the affected entry points and keep ambiguous matches unresolved. [Spring Security architecture](https://docs.spring.io/spring-security/reference/7.0/servlet/architecture.html), [multiple chains and matchers](https://docs.spring.io/spring-security/reference/7.0/servlet/configuration/java.html), [MVC interceptors](https://docs.spring.io/spring-framework/reference/7.1/web/webmvc/mvc-config/interceptors.html).

Until a layer pack with `framework-order` has run and resolved the applicable configuration, Spring endpoint protection remains `unknown`. Checks requiring that capability are `unsupported`; method annotations may raise candidates but cannot clear them. The same rule applies to Express/Nest order, and the existing Next middleware heuristic needs matcher-aware evidence before it can establish protection.

Proposed fixture gates include multiple ordered chains, **a missing catch-all chain**, **a `securityMatcher`/`requestMatchers` mismatch**, excluded routes, custom filters, method-security-only and profile-conditioned configurations, asynchronous dispatch, generated/Lombok code, multiple source roots, and missing dependencies. Test both known-vulnerable paths and controls that really mitigate them. Record the detected Spring version and selected semantic model; documentation for one framework version is not evidence for all versions. The cited Spring Security 7.0 and Spring Framework 7.1 pages are research inputs, not a support commitment. Supported pack versions remain an owner decision.

For E3, use pinned WebGoat for labelled Spring lessons, Juice Shop for TS/JS application challenges, and BenchmarkJava for controlled Java detector comparisons. WebGoat's inspected main POM declares Spring Boot 4.1.1 and Java 25; this is a source fact, not a verified scanner/runtime combination. BenchmarkJava is a servlet-oriented benchmark, not evidence of Spring chain coverage. Keep upstream corpora as separately acquired, commit-pinned inputs with license records; do not copy their source into Sentinel's distributable rule pack. WebGoat uses GPL terms, BenchmarkJava identifies GPL-2.0, and Juice Shop identifies MIT. [WebGoat](https://github.com/WebGoat/WebGoat), [inspected POM](https://raw.githubusercontent.com/WebGoat/WebGoat/main/pom.xml), [WebGoat license](https://github.com/WebGoat/WebGoat/blob/main/LICENSE.txt), [OWASP Benchmark](https://owasp.org/www-project-benchmark/), [BenchmarkJava](https://github.com/OWASP-Benchmark/BenchmarkJava), [Juice Shop](https://github.com/juice-shop/juice-shop), [challenge categories](https://pwning.owasp-juice.shop/companion-guide/latest/part1/categories.html).

## Dependencies, secrets, infrastructure, and CI

**OSV-Scanner** is Apache-2.0 and supports broad dependency manifest/lockfile detection. Its README still labels its V2 instructions beta; pin a named release rather than treating a mutable README label as a release guarantee. Its `--offline` mode uses a previously downloaded database and avoids sending project/dependency information; commit-level scanning is an offline limitation. `--offline-vulnerabilities` permits other network features and is not the offline profile. Maven `pom.xml` transitive resolution uses deps.dev by default and is disabled in offline mode. An offline manifest-only run must report unresolved transitives and versions; a pinned lockfile, SBOM or imported resolved inventory may provide additional evidence. Record actual extraction depth instead of claiming the manifest is the installed dependency tree. Current source-scan documentation describes call analysis for Go and experimental Rust, so Java/TS package matches must not be presented as proven vulnerable-function reachability. Store advisory snapshot identity and package evidence so a new advisory snapshot can rerun matching without reparsing code. [Project](https://github.com/google/osv-scanner), [offline behavior](https://google.github.io/osv-scanner/usage/offline-mode/), [call analysis](https://google.github.io/osv-scanner/usage/scan-source), [manifests and resolution](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/).

**Gitleaks** is MIT-licensed and supports directory, Git-patch/history, and stdin scanning, JSON/SARIF output, baselines, and redaction. Its baseline feature omits old findings from the output. Sentinel should retain immutable observations and apply disposition in its own store, so an acknowledged secret remains inspectable. Configure redaction and verify every exported artifact; the CLI's log-redaction description alone is not evidence that every custom report is safe. [Gitleaks repository and CLI](https://github.com/gitleaks/gitleaks).

**Trivy** is Apache-2.0 and supports repository vulnerabilities, secrets, licenses, and misconfigurations. Repository scans use supported manifests/lockfiles; artifact/container scans are separate targets. For `pom.xml`, missing local metadata can cause remote repository lookups, including Maven Central. `--offline-scan` prevents those lookups but may omit dependencies and does not disable vulnerability database downloads. JAR identification can require the separate Java database. Misconfiguration scanning is disabled by default for repository scanning. JSON and SARIF can carry results from all those scanner families. Prefer it initially for IaC and container checks; if dependency scanning is also enabled, preserve each engine's evidence when correlating duplicates. [Project](https://github.com/aquasecurity/trivy), [repository scope](https://www.trivy.dev/docs/latest/guide/target/repository/), [report formats](https://www.trivy.dev/docs/latest/guide/configuration/reporting/), [Java coverage](https://trivy.dev/latest/docs/coverage/language/java/).

Trivy documents database locations at `mirror.gcr.io/aquasec` then `ghcr.io/aquasecurity`, with fallback for transient errors. Checks-bundle fallback is different: embedded checks are used instead of a list of alternative bundle registries. Prepare immutable database/check snapshots separately, disable their updates during offline runs, and record their ages. Every adapter declares `dependencyResolution`, `databaseFetch` and `telemetry` separately from target-code execution; no single “no build” or “offline scan” switch substitutes for those effects. [Database configuration](https://trivy.dev/latest/docs/configuration/db/), [air-gap guidance](https://trivy.dev/latest/docs/advanced/air-gap/).

**zizmor** is MIT-licensed and checks supported CI configuration, including GitHub Actions, Dependabot, and pre-commit. Documented checks address template injection, credential exposure, and excessive permissions. Offline mode explicitly skips audits requiring online access; SARIF is supported. Record both selected and skipped audits, and distinguish lack of online evidence from a passed check. [Project](https://github.com/zizmorcore/zizmor), [operating modes](https://docs.zizmor.sh/usage/), [audit catalog](https://docs.zizmor.sh/audits/).

**Alternatives remain explicit options.** Apache-2.0 Grype accepts images, directories and SBOMs and is worth comparing when the team already produces Syft/SBOM artifacts. Apache-2.0 Checkov covers infrastructure and CI definitions, including Terraform, Kubernetes, Helm, Dockerfiles and GitHub Actions. Their selected checks, database/cache inputs and network behavior require the same E7 validation as the defaults. AGPL-3.0 TruffleHog verifies candidate secrets through service APIs unless disabled; `--no-verification` is available, but disabling verification alone is not an offline guarantee for every source mode or update mechanism. Retain Gitleaks as the offline default; a live verification profile is a separate decision. [Grype](https://github.com/anchore/grype), [Checkov](https://github.com/bridgecrewio/checkov), [TruffleHog](https://github.com/trufflesecurity/trufflehog).

**Scanner coverage is an adapter contract, not an empty result list.** Compare each adapter's scanned and skipped evidence with `Snapshot.fileInventory`; declare `coverageGranularity: per-file | per-file-per-rule | aggregate`. Parse skip reasons, parse failures and timeouts from the pinned tool's actual structured output or validated diagnostics, retaining raw outputs. Do not assume Semgrep's `paths.skipped` or equivalents exist in every release, format or engine. If a reliable scanned set cannot be established, the adapter is aggregate-only and cannot mark individual file/rule checks complete. Missing inventory entries remain `not-run`. E1/E3/E7 must establish those capabilities before release.

## Standards and maintained rules

Use CWE identifiers for weakness classification and versioned OWASP ASVS requirements for the verification catalog. OWASP lists ASVS 5.0.0 and recommends version-qualified references because requirement identifiers can change; it offers machine-readable formats and states CC BY-SA 4.0 licensing. OWASP Top 10:2025 is useful for executive grouping, but OWASP explicitly characterizes Top 10 as an awareness starting point rather than a complete testing program. [ASVS](https://owasp.org/projects/asvs), [ASVS project reference](https://owasp.org/www-project-application-security-verification-standard/), [Top 10:2025](https://top10.owasp.org/2025), [Top 10 status](https://owasp.org/projects/top-ten?lang=en), [testing limitations](https://github.com/OWASP/Top10/blob/master/2025/docs/en/0x03_2025-Establishing_a_Modern_Application_Security_Program.md?plain=1).

CWE supplies versioned XML/CSV downloads, content history, and an API. Its download page currently labels the list 4.20 while its 2025 Top Ten mapping still says RC1; pin the actual artifact and digest rather than relying on a mutable “latest” URL or page footer. MITRE publishes terms permitting research, development, and commercial use subject to those terms. [Downloads](https://cwe.mitre.org/data/downloads.html), [formats and history](https://cwe.mitre.org/about/faq), [terms](https://cwe.mitre.org/about/termsofuse.html).

Proposed rule maintenance is a separate reviewable workflow: fetch an approved upstream release, diff taxonomy/control changes, propose mappings and detectors, run positive/negative fixtures, then publish an immutable rule-pack version. A new CWE description is not automatically an executable detector. Each rule declares applicability, detector/locator/manual-review capability, evidence requirements, limitations, source URLs, and license provenance.

## Runtime scope and unresolved decisions

ZAP's baseline scan crawls and reports passive findings. Passive analysis does not alter messages, but crawling still sends requests. The API scan imports OpenAPI, SOAP, or GraphQL and performs an active scan by default; its safe-mode option skips active scanning. ZAP is Apache-2.0, with separately listed third-party components. [Baseline](https://www.zaproxy.org/docs/docker/baseline-scan/), [API scan](https://www.zaproxy.org/docs/docker/api-scan/), [passive/active behavior](https://www.zaproxy.org/docs/api/), [license notice](https://github.com/zaproxy/zaproxy/blob/main/LEGALNOTICE.md).

For v1, import captured passive results with the tested environment, authentication context, route inventory, timestamps, and build identity. Later, expose an authorized runtime job with explicit target scope, rate/time limits, test credentials, and captured scanner policy. Runtime observations augment static facts; one observed response cannot establish all possible paths or deployment configurations.

Before implementation commitment, measure Java adapter fidelity, deep-flow precision/recall, extraction time/storage, model-review value, and rule portability on the same corpus. Also settle distribution rights per pinned tool/pack, supported Spring versions, scanner update verification, and whether a default deeper-flow adapter ships at all after E3. CodeQL, Joern, the qualified Bearer comparison and the pattern engines remain separately attributable capabilities. The hosted-service posture, isolated Java build profile, model providers, E3/E5 thresholds and supported framework versions remain owner questions in the proposal; none is decided here. Keep every unsupported or unfinished capability visible in the report.
